Agent Action Review

A review layer that records what autonomous agents did across sessions and surfaces the actions a human should have approved but did not see.

Illustrative opportunity score

60 / 100

Demo heuristic

Necessary infrastructure for agents that already act in production, and the market for those agents is still forming.

The problem

Teams cannot audit what their agents actually did in production, so every incident investigation reconstructs behaviour from scattered logs that were never designed to be read as decisions.

Executive summary

Agent Action Review is a platform concept for engineering teams running autonomous or semi-autonomous agents in production. It addresses a problem that recurs often enough to be felt in operating cost rather than noticed as an inconvenience, and it becomes buildable because recent capability changes made the underlying work tractable.

The first version would be deliberately narrow — one workflow, one countable unit — with 5-7 weeks of work needed before any code is written to establish whether the problem is real. The illustrative score of 60/100 reflects low confidence in the read, with the reasoning broken out dimension by dimension below.

Target customer profile

An engineering team that has let an agent take real actions — write migrations, modify infrastructure, contact customers — and has no defensible record of what it did. When something goes wrong, the timeline is reconstructed from partial logs and memory.

Existing alternatives and competitor categories

  • Application logging
  • Tracing and APM tools
  • Vendor agent dashboards
  • Manual transcripts

Most of these are adjacent rather than direct. That usually means the budget exists, the buyer tolerates the current state, and the real competitor is doing nothing at all.

Why the opportunity might matter now

Agents acting over long horizons produce behaviour that no human watched while it happened. Retroactive observability built for request-response systems does not capture sequences, decisions, or approvals, and the gap only becomes visible after the first serious incident.

Proposed solution

A record of agent activity structured around decisions rather than requests: what the agent intended, what tools it called, what it changed, and where a human approved or bypassed the step that mattered.

Potential business model

Platform fee per production agent with usage-based pricing on recorded sessions. Strong expansion path as agent fleets grow.

MVP scope

  1. 01Decision-level recording with intent and outcome
  2. 02Tool call and side-effect capture
  3. 03Approval points marked against the actions that mattered
  4. 04Incident reconstruction as a timeline of decisions
  5. 05Retention controls to satisfy internal policy

The scope above is deliberately one workflow with a countable unit. Anything broader belongs in the second version, if the first version works.

Key assumptions

  1. 01Teams want the record for audit and incident response, not just debugging
  2. 02Agents will stay in production long enough to need this
  3. 03Recording can be retrofitted without agents changing behaviour
  4. 04Compliance and platform teams, not just engineers, sign off on it

Each of these is a claim that could turn out to be false. They are listed so a founder knows what to attack first.

Risks and unknowns

  1. 01Platform providers ship native traces
  2. 02Very few teams currently run agents with production side effects
  3. 03Recording overhead may alter agent behaviour
  4. 04Category may be premature for the market's current agent adoption

Validation plan

  1. 01Find teams that have had an agent incident and ask what they could reconstruct
  2. 02Backtest a recorder against a known incident to see if the timeline matches reality
  3. 03Ask what would need to be recorded for an internal audit to accept it
  4. 04Compare against existing logging: what decision-relevant information is missing today?

Run this before writing code. If the interviews come back without a recurring incident, the honest outcome is to drop the idea rather than reframe it.

Three customer interview questions

  1. 1Describe the last time an agent of yours caused a problem. What could you prove about what it did?
  2. 2Who would ask to see an agent activity record, and for what?
  3. 3What do you do today when an agent's behaviour looks different than expected?

Suggested first experiments

  1. 01Instrument an internal agent and compare records against the known outcome
  2. 02Interview platform and security leads about required audit evidence
  3. 03Prototype a decision timeline from existing logs to test whether reconstruction works
