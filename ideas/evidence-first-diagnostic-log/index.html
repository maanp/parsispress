Evidence-First Diagnostic Log

A diagnostic record that keeps the reasoning behind every fault finding, so a repeated failure is answered from history instead of re-investigated from scratch.

Illustrative opportunity score

63 / 100

Demo heuristic

Compelling insight about why reliability work repeats, dependent entirely on adoption friction inside the investigation itself.

The problem

Recurring faults get re-diagnosed from scratch because nobody wrote down what was actually ruled out, so the site pays for the same investigation several times a year.

Executive summary

Evidence-First Diagnostic Log is a product concept for maintenance and reliability teams in process and manufacturing. It addresses a problem that recurs often enough to be felt in operating cost rather than noticed as an inconvenience, and it becomes buildable because recent capability changes made the underlying work tractable.

The first version would be deliberately narrow — one workflow, one countable unit — with 4-6 weeks of work needed before any code is written to establish whether the problem is real. The illustrative score of 63/100 reflects low confidence in the read, with the reasoning broken out dimension by dimension below.

Target customer profile

A reliability team with genuine historical depth — years of work orders, downtime logs, and a small number of experienced engineers who know which faults are expensive. Their knowledge lives in those engineers, and it leaves when they do.

Existing alternatives and competitor categories

  • Work order history search
  • CMMS fault coding
  • Reliability engineering consultants
  • Tribal knowledge

Most of these are adjacent rather than direct. That usually means the budget exists, the buyer tolerates the current state, and the real competitor is doing nothing at all.

Why the opportunity might matter now

Reasoning over free-text fault narratives became possible once the historical record was legible to a model. The remaining gap is that existing records describe actions taken rather than hypotheses eliminated, which is precisely the information that prevents repeat investigation.

Proposed solution

A diagnostic layer that captures hypotheses considered and evidence checked during each investigation, then surfaces them when the same symptom recurs so engineers start from last time's exclusions.

Potential business model

Per-site annual licence integrated with an existing maintenance system, priced against avoided repeat investigations.

MVP scope

  1. 01Fault investigation capture with hypotheses and eliminations
  2. 02Symptom-based retrieval of prior investigations
  3. 03Timeline linking related faults across assets
  4. 04Explicit distinction between observation and inference
  5. 05Report of repeat investigations avoided

The scope above is deliberately one workflow with a countable unit. Anything broader belongs in the second version, if the first version works.

Key assumptions

  1. 01Engineers will record eliminations, not just actions, without it feeling like paperwork
  2. 02Existing fault narratives contain enough signal to bootstrap
  3. 03Avoided repeat investigation is measurable and valued
  4. 04CMMS integration is achievable without a data migration project

Each of these is a claim that could turn out to be false. They are listed so a founder knows what to attack first.

Risks and unknowns

  1. 01Workflow friction kills adoption in a reliability team under load
  2. 02Existing records are too thin to bootstrap retrieval
  3. 03A CMMS vendor may bundle this as a feature
  4. 04Reliability teams are cautious about changing failure investigation

Validation plan

  1. 01Have reliability engineers reconstruct three repeat faults and check what history would have helped
  2. 02Measure how much of a typical investigation is re-derivation
  3. 03Shadow one investigation and capture structure before building the interface
  4. 04Test whether recorded eliminations actually get read on the next occurrence

Run this before writing code. If the interviews come back without a recurring incident, the honest outcome is to drop the idea rather than reframe it.

Three customer interview questions

  1. 1Describe a fault that came back three times. What did each investigation conclude?
  2. 2What do you wish your work order system recorded that it does not?
  3. 3Who on your team would notice fastest if repeat failures started climbing?

Suggested first experiments

  1. 01Manual diagnostic log run by hand for one engineer for two weeks
  2. 02Backtest retrieval against known repeat faults
  3. 03Compare capture burden against the time the engineer says it would save
